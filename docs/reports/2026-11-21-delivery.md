## 1. `intel_iommu=off` 整机重启 A/B

### 1.1 为什么必须做这个测试

`iommu=pt`（identity 映射）**已经是本机原状**，没有「新选项」可切。
这次测的是比 pt 更激进的一档：**彻底不走 IOMMU**（`intel_iommu=off iommu=off`）。
如果连 off 都没有收益 ⇒ IOMMU 这条 DMA 通道的开销不是瓶颈 ⇒ pt 更不用试。

### 1.2 测法（保证 A/B 干净）

| 步骤 | 内容 |
|---|---|
| ① | 改 `/etc/default/grub.d/99-nvidia.cfg` → `update-grub` → 整机重启 |
| ② | 验证：`/proc/cmdline` 无 `intel_iommu=on`、`iommu_groups` 316 → **0**、dmar 设备 20 → **0**、dmesg 无 DMAR 记录 |
| ③ | **重启后由 systemd oneshot 自动跑基准**（客户端会话断了也会跑完并留结果） |
| ④ | 两组用**同一份 bench 脚本、同一台机、同一配置**，只差 IOMMU |
| ⑤ | 额外加 **大上下文 prefill 专项**（4 路 × 15 万字符、每请求唯一 prompt 打散 prefix cache） |

> ⚠️ **Qwen unit 必须先 disable**：它是 `enabled` 但停着，重启会自动起来；
> 而且它的 CPU 专家引擎钉在 node1（24 worker），**与 DeepSeek rank1（GPU2）共用那 32 个物理核**
> → 会直接抢走 DeepSeek 的 CPU 算力，污染测量。（用户已自行 disable。）

### 1.3 结果

| 指标 | `iommu=on iommu=pt` | `iommu=off iommu=off` | 变化 |
|---|---|---|---|
| **4 路 服务端 avg_tps** | 139.70 | 145.40 | +4.1% |
| 4 路 客户端 tok/s | 88.54 | 98.87 | +10.4% |
| 4 路 wall | 44.73 s | 40.43 s | −10.6% |
| 4 路 ITL p50 / p95 | 58.7 / 109.3 ms | 59.0 / 107.0 ms | ≈ |
| 4 路 ITL > 200 ms | 0.67% | 0.60% | ≈ |
| **12 路 服务端 avg_tps** | 141.80 | 143.60 | **+1.3%** |
| 12 路 客户端 tok/s | 78.09 | 79.72 | +2.0% |
| 12 路 wall | 124.17 s | 116.00 s | −7.0% |
| 12 路 ITL p50 / p95 | 169.3 / 202.0 ms | 166.7 / 203.7 ms | ≈ |
| 12 路 ITL > 200 ms | 5.70% | 6.00% | ≈ |
| **大上下文 prefill tok/s** | **3738.23** | **3741.57** | **+0.1%** |
| 大上下文 prefill TTFT | 59.71 s | 59.67 s | −0.1% |
| prefill 期间 PCIe tx / rx | 0.57 / 0.14 MB/s | 0.57 / 0.14 MB/s | **0.0%** |

### 1.4 决策：**回滚 / 保持 `intel_iommu=on iommu=pt`**

1. **prefill 是 IOMMU 唯一可能有影响的通道，而它 +0.1%**（完全在噪声内）。
2. **12 路 +1.3% < 事前约定的门槛 +2%**。
3. **4 路 +4.1% 落在跨重启噪声内**：同配置、同 IOMMU=on，重启前独立基线 143.7 / 146.9，
   本次 ON 139.7 / 141.8 —— **同状态自身波动就有 2.8% / 3.5%**，
   已经大于「on→off」的 4 路差值。⇒ 不能把 4 路那个数当信号。
4. **机理：IOMMU 不在关键路径上。**
   - decode 期间 PCIe 流量实测只有 **~278 KB/s**（GPU1 空闲时 36 KB/s ⇒ 计数器是活的）
   - prefill 期间也只有 **0.57 MB/s**
   - 专家权重换入走 **XTier 自己的 CPU 引擎 + 主存** 路径（AVX512 算力 + 32 物理核），
     GPU 只保留热槽；反过来把未命中专家搬去 GPU（`XTIER_DECODE_MISS_GPU=0.1`）实测 **−19.3%**，
     因为 PCIe 才是真瓶颈 —— 说明「减少 PCIe 流量」这条路已经走到头，
     **再省 IOMMU 的翻译开销也没有流量可省**。

**附带结论**：关掉 IOMMU 在本机是**纯风险无收益**（移除 DMA 隔离、可能影响 NVIDIA 推荐的
peer-to-peer / ACS 语义），不做。

### 1.5 测法上的一个坑（值得记）

第一版基准是 **decode 主导**的，而 decode 几乎不产生 DMA
⇒ 光测 decode 一定会得出「没差别」的**错误结论**（虽然这次结论恰好一致）。
正确做法是**加 prefill 专项**，那才是 IOMMU 真正作用的通道。

## 2. `DeepSeek-V4.1-Flash.service` 对齐

### 2.1 对齐前发现的 5 个真问题

| # | 严重度 | 问题 | 证据 | 修法 |
|---|---|---|---|---|
| 1 | **P0** | `KV_POOL` unit=**1572864** vs 脚本默认 **524288**（差 3 倍） | 脚本 `--max-total-tokens ${KV_POOL:-524288}` | 脚本默认改成 1572864 |
| 2 | **P0** | `DSPARK` unit=1 vs 脚本默认 **0** | 脚本 `if [ "${DSPARK:-0}" = 1 ]`；不设则 `XTIER_DRAFT` / `SGLANG_RAGGED_VERIFY_MODE` 都不 export ⇒ **投机解码整个关闭，accept_len 3.5→1.0** | 脚本默认改 1 |
| 3 | **P0** | `SPS_TABLE` 只有 unit 有，脚本无默认 | 脚本 `if [ -n "${SPS_TABLE:-}" ]` ⇒ 脚本单跑时**没有** `--speculative-dspark-sps-table-path` | 脚本给默认路径 |
| 4 | P1 | `MAMBA_CACHE` 只有 unit 有 | 脚本 `[ -n "${MAMBA_CACHE:-}" ]` ⇒ 脚本单跑时**没有** `--max-mamba-cache-size` | 脚本给默认 16 |
| 5 | P1 | unit 注释**事实错误**：`8001 用 GPU0+2（同 NUMA node0，省 UPI）` | `nvidia-smi topo -m`：GPU0=node0(0-31,64-95)、**GPU2=node1(32-63,96-127)**；GPU0↔GPU2 拓扑 = **SYS**（跨 UPI），**既不同节点也不省 UPI** | 改成真实理由：一卡一 NUMA 节点 ⇒ 专家权重与 GPU 同域（否则两 rank 拿到完全相同的 CPU 集合，实测 29/29 重叠、每层 CPU 257µs→8812µs） |

**其它（stale 注释）**：脚本头部 `GPU0 + GPU1，32K 上下文`（实为 GPU0+GPU2、256K）、
`不开 DSpark 投机`（实为已开）、`上限仍 128`（实为 64）、尾注把 DSpark 列进「刻意没开」。

### 2.2 对齐的三条铁律（已写进 unit 头部）

1. **unit 只放脚本用 `${VAR:-默认值}` 读取的变量** —— 脚本里 `export VAR=xxx`（写死）的
   变量放进来会被脚本覆盖，等于骗人。例：`XTIER_CACHE_ELASTIC_RESERVE_GIB=2`、
   `XTIER_CACHE_PROMPT_WINDOWS=10`、`XTIER_CACHE_LOG=200` 都是脚本写死 ⇒ 不进 unit。
2. **unit 的每个值必须等于脚本默认值**（两边同值）⇒ 「直接跑脚本」≡「走 systemd」。
3. **命令行参数不进 unit**（全在脚本 `ARGS[]`），避免 unit 变成几百行命令清单。

⇒ unit 从 **13** 个 Environment 扩到 **37** 个（把 `SCHEDULE/PDI/MAX_REQ/CHUNK/CONTEXT/MEM/
KV_POOL/GRAPH_BS/PREFILL_*` 等所有可覆盖旋钮显式化），但**行为零变化**。

### 2.3 部署前的 4 道安全门（`tools/_deploy_align.py`）

任一不过就中止、绝不碰生产：

1. `iommu-bench.service` 不在跑
2. 新旧脚本 `DRYRUN=1` 差异**只应是**那 3 处对齐修复（KV_POOL / mamba / DSpark 参数组）
3. **新脚本 `DRYRUN=1` 输出 == 当前线上进程的 `/proc/PID/cmdline`** ⇒ 真的没改行为 ✅
4. **unit 每个变量都能在脚本里找到同名 `${VAR:-默认}` 且值相同** ⇒ 37 个变量、0 分歧 ✅

## 5. 已知边界与下一个杠杆

### 5.1 并发上限 8 路（硬件/上游限制，调参解决不了）

`bs > 8` 时 CUDA graph 只能 replay bs 1..8 ⇒ `ragged_verify_layout=None`
⇒ compact(ragged) verify 失效退化成 static(rows_per_request=5)
⇒ 跳过 JIT indexer planner（要求 rows_per_request==1）
⇒ `deep_gemm.get_paged_mqa_logits_metadata` 在 SM89 返回 None ⇒ assert 崩。

过 8 只有三条路：**放弃 DSpark（不值）／换 SM100+ 机器／改 SGLang 上游 kernel 元数据规划器**。

### 5.2 ★ 下一个大杠杆：AMX 内核改造

CPU 是 Emerald Rapids（`amx_bf16/amx_tile/amx_int8` 全 YES），但引擎只编译了 AVX512。
作者自带的 `bench_cpu_ceiling.py` 实测算术占 60~68% ⇒ **专家计算算力受限**，不是带宽受限。

改造点：
- `csrc/engine/engine.cpp:731` —— `_mm512_dpbf16_ps`（gate/up）
- `csrc/engine/engine.cpp:766` —— `down_rows_bf16`
- `csrc/engine/dispatch.cpp:57` —— 库选择

属「写内核」而非调参（工程量小时级、数值须 bitwise 一致、风险真实），
**需单独排期**。

### 5.3 其它

- **输出确定性**：引擎数值层固有非确定性，在 logit 近平局处翻转 greedy（详见 NOTES §0.5 / §14.46）。
  网关有 60 秒 Redis 响应缓存 ⇒ 日常感知不到。`seed` 在这条链路上不可靠。
- **Qwen 侧**：`Qwen3.8-Flash-Next-XTier.service` 按用户要求保持 `disabled`。
  XTier 只认 NVFP4/MXFP4，本机 FP8 checkpoint 不兼容。
- **并发上限之外的单请求延迟**：大上下文 prefill 约 3700 tok/s，150K 字符 TTFT 约 60 s，
  这是 CPU 专家引擎的算力上限，AMX 改造是解法。
