# 2026-11-20：L20 (SM89) 上 DeepSeek-V4.1-Flash TP=2 的硬件适配与加速包

机器：2×L20 48G (SM89 Ada) + Intel Xeon Gold 6530（2 socket / 2 NUMA node，每 node 32 物理核 + 64 逻辑核，1TB RAM），
4 卡中 GPU3 跑 Strata/Qwen，GPU0+GPU2 服务本模型。

本文是 L20 加速包的说明与实测记录。配置目录：`configs/ds41-l20-tp2/`（启动脚本、监控台卡片、SPS 成本表、README）。

## 一、两个 TP rank 不能放在同一个 NUMA 节点（最严重的问题）

`xtier/engine/placement.py` 的 `auto_nodes()` 在两卡同节点时会退化成 `groups[rank]`；而 C 引擎的
`xtier_worker_cpus()` **没有 rank 偏移参数**，两个 rank 会拿到**完全相同的 CPU 集合**。

实测（GPU0+1，`XTIER_TP_NODES=0\|0`）：两个 rank 的 29 个 worker 线程钉在同样的 29 个 CPU 上（100% 重叠），
每层 CPU 时间从 257 µs 劣化到 **8812 µs**（34×），单请求严重卡顿；加载期还出现 Bus error / Segmentation fault。

→ TP=2 必须一卡一节点 = **GPU0+GPU2**。GPU0+2 之后每层 CPU 降到 625–633 µs（−26%），冷 prefill +13%。

## 二、prefill 的 chunk 越大越快（专家权重每 chunk 全量重传）

每个 prefill chunk 都要为 40 层重新上传全部 384 个专家 = 3.36 GiB/层/卡 = **134 GiB/卡/chunk**。

| chunk | 100K prompt 上传轮数 | 冷 prefill |
|---:|---:|---:|
| 2048 | 50 | 771 tok/s |
| 8192 | 13 | 1597 tok/s |
| 16384 | 7 | 2498 tok/s |
| 32768 | 4 | **3488 tok/s** |

⚠️ 网上那篇 4×RTX PRO 6000 的实战记录建议 chunk=2048，**前提是 all-reduce 走 PCIe switch（19.57 GB/s）**；
我们跨 socket（SYS）all-reduce 走 UPI，chunk 越小 all-reduce 次数越多反而更慢。

## 二之二、多请求「卡顿」的真凶：PDI=0（最重要的一条）

**聚合吞吐完全测不出卡顿。** 用 `tools/bench_latency.py`（流式，记录每个 token 的到达时间）才看得见：

```
6 路 × 100K 上下文，同时流式生成：
  PDI=0    ITL p50 340ms   ITL max 116,080 ms   ← 一个请求 116 秒发不出一个 token
  PDI=32   ITL p50  45ms   ITL max     330 ms
```

原因：`--prefill-decode-interval 0` = prefill 之后不等，直接排下一个 prefill。几个长上下文的
prefill 会连成一段**几百秒的连续 prefill**（每个 32K chunk 约 8.5 秒，6 个请求各 100K 共 20 个 chunk），
期间已就绪的请求一个 decode 步都跑不到。batch 日志里是连续 9 个 `Prefill batch`、
每个 `#new-token: 32768`、间隔 8–9 秒，中间没有任何 `Decode batch`。

PDI 的语义（SGLang `scheduler.py:1483-1515`）：**prefill 批之后强制跑 N 个 decode 轮再排下一个 prefill**；
`prefill_decode_interval_min_bs` 默认 0，任何 batch 大小都生效。

| PDI | 8×4 聚合 | ITL max | 8×4 TTFT p95 | 冷 prefill |
|---:|---:|---:|---:|---:|
| 0 | 42.0 / 44.4 | **116,080 ms** | 7.1 s | 3488 tok/s |
| 16 | 45.2 / 52.9 | 339 ms | 6.0–10.3 s | 3526 tok/s |
| **32** | **56.5 / 55.7** | **330 ms** | **7.9–8.9 s** | 3526 tok/s |
| 64 | 57.4 / 56.8 | 330 ms | 14.2–16.3 s | 3526 tok/s |

PDI=32 是平衡点：停顿 330 ms、agent 吞吐 +27%、TTFT 不恶化。64 的 decode 轮次太多，新请求的 prefill
排不进来，TTFT p95 翻倍。

> 这一条也解释了为什么 8×4 的短提示基准（1.5K prompt）看不出问题：短提示只占一个 chunk，
> 根本不会出现「连续几百秒的 prefill」。**验收必须用延迟分布 + 长上下文并发，不能只看聚合吞吐。**

## 三、常驻热槽减半、弹性上限不变 → 显存给 KV

`XTIER_CACHE_ELASTIC_BASE=0.5` 让常驻槽从 64 降到 32，弹性上限仍 128（空闲时扩回），
`available_gpu_mem` 从 7.9 GB 涨到 18.3 GB，冷 prefill 2498 → 3028 tok/s。

## 四、KV 不是显存瓶颈

DS4.1 的 `bytes_per_full_token=1673.31`（V4 压缩 KV：4 个 owner layer，ratio 1/2，FP8）。
512K 池只占 0.82 GiB；1.5M 池占 2.45 GiB。**真正吃显存的是专家热槽**（9.4 MB/槽/层，40 层，43 层含 draft）。

## 五、加速包侧的改动

### 5.1 L20 的 FP8 GEMM 逐 M 调优（配置进包）

`xtier/packs/deepseek_v4/fp8_configs/` 下的 `device_name=NVIDIA_L20` 文件：decode 的 M = batch × top-k，
从 1 到 48 都用得上，而不同 M 的最优 tile 完全不同（上游的工具只在 M=8 测速却把同一 tile 写进所有 bucket）。

| M | 最优 tile | 相对默认 |
|---|---|---:|
| 1 | BM16/BN32/warps4, **SWAP_AB** | 1.27–6.96× |
| 2–32 | BM16/BN32/warps2–4, **SWAP_AB** | 1.02–4.03× |
| 64 | BM16/BN64/warps2/stages4 | 1.02–1.27× |
| 128 | BM16/BN128/warps2 | 1.02–1.32× |

中位数 **1.39×**。工具：`tools/tune_l20_fp8_perm.py`（同时写 SGLang 的 configs/ 和加速包）。
校验：`tools/check_fp8_splitk_sm89.py`（误差与默认一致，rel_err 0.0025–0.0031）。

### 5.2 源码：SM89 也能用 SPLIT_K / SWAP_AB

`sglang/kernels/ops/gemm/fp8_kernel.py` 原本只给 SM90 用 SPLIT_K/SWAP_AB（`hopper_tuned`），
但那个 kernel 是**通用 Triton**（2D grid + 归约 / 操作数转置），没有用任何 Hopper 专属指令——
门槛只是「没在别的架构验证过」。改动：

- `sglang/srt/utils/device.py`：新增 `is_sm89_supported`（CPUID 8.9 + CUDA 12.0）
- `sglang/srt/runtime_context.py`：把它注册成平台事实 `is_sm89`
- `fp8_kernel.py`：`is_sm90 or is_sm89` 放行 SPLIT_K/SWAP_AB

本机实测：**SWAP_AB 有收益**（M=1 时 −10%）；**SPLIT_K 是负收益**（N 维已经够填满 GPU，多一次归约更慢），
所以生成的配置里 `SPLIT_K=1`、`SWAP_AB=True`（M ≤ 32）。

### 5.3 源码：CPU kernel 的 -mtune 自动探测

`csrc/CMakeLists.txt` 原来把 AVX512 kernel 的 `-mtune` 写死成 **znver4（AMD Zen 4）**，
而这台机器是 Intel Xeon Gold 6530。改成按构建主机自动探测（`/proc/cpuinfo` 的 vendor + flags），
Intel + AMX → `emeraldrapids`，AMD → `znver4`，并把 flags 的 CMake 缓存改成 FORCE（否则旧缓存值会存活）。

实测：长上下文 **6 路 × 60K 111.5 → 97.5 s、4 路 × 84K 103.6 → 90.1 s（−12~13%）**。

### 5.4 源码：Python 的 CpuPlan 少传两个参数（原本不可用）

`xtier/engine/__init__.py` 的 `CpuPlan.__init__` 调用 `xtier_create3` 只传 11 个参数，
C API 需要 12 个（少了全局 scale `g13`/`g2`）→ **任何 Python 工具都建不出引擎 plan**。
生产路径不受影响（C++ 侧自己建 plan），但基准工具全部用不了。已修，并补上 `xtier_read_probe` 的 ctypes 绑定。

## 六、CPU 引擎：忙等与换页 churn

| 改动 | 前 | 后 | 效果 |
|---|---|---|---|
| `XTIER_SPIN_COUNT` | 1048576 | 32768 | 负载下整机 CPU 从 80% us 降到 1.7–39%，吞吐不变 |
| `MIN_GAIN` / `DECAY` | 1.5 / 0.7 | 3 / 0.9 | swaps/round 111 → **63**，命中率 0.654 → 0.671，每层 CPU 1023 → 985 µs |

## 七、AMX：降级为「有条件的后续项」（用数据判断）

引擎自带 `xtier_read_probe`（只流过被路由到的专家权重、不做算术），配合 `tools/bench_cpu_ceiling.py`
可以量出 CPU 专家计算里「带宽」和「算术」各占多少。生产形状（单节点 32 线程）：

| m | t_read | t_fwd | 算术占比 |
|---:|---:|---:|---:|
| 1 | 0.14 ms | 0.32 ms | **58%** |
| 8 | 1.83 ms | 2.95 ms | 38% |

算术确实占 ~58%（decode 的 M=1–2），**但 AMX 的 tile 是 16 行，decode 每个专家只有 1–2 个 token 行**
（16 行里只用 1–2 行），加上 MXFP4 → AMX B-tile 的在线重排开销，收益很可能被吃掉。
另外 XTier 目前**没有任何 AMX 代码路径**（二进制里 AMX 指令数为 0，用的是 `VDPBF16PS`），
Linux 的 `XFEATURE_XTILEDATA` 权限也还没申请。

要做的话分四步（按性价比）：
1. `dispatch.cpp` 加 AMX CPUID 检测 + `arch_prctl` 申请 tile 权限，独立 `libxtier_engine_amx.so`
2. 隔离 microbenchmark：对比 `VDPBF16PS` / AMX-BF16（预打包）/ AMX-BF16（在线反量化 + 重排），
   必须把读 FP4 + 反量化 + 重排都算进时间
3. 有正收益再接 Gate/Up（`engine.cpp:710-749`），保留 AVX512 回退
4. 再接 Down（`engine.cpp:751-810`）

CPU prefill 比 decode 更可能获益：现在每 expert microgroup 上限 8 token
（`XTIER_PREFILL_MICRO_TOKENS`），扩到 16/32 才有 AMX 的批量优势。

## 八、已排除的项

| 项 | 结论 |
|---|---|
| `XTIER_TILES_PROD=1` | ⛔ 128 宽 tile 静态估算需 120–144 KiB 共享内存，**超过 SM89 的 99 KiB**（虽然实测能编译，但只 +2%） |
| `XTIER_RECALL=1`（memory backend） | ⛔ 8 并发下把 scheduler 卡死 → NCCL 集合通信超时 → watchdog SIGKILL |
| FP4 张量核 / FP4 indexer / b12x / Markov / MXFP8 prefill tile | ⛔ SM120 硬门槛 |
| `--fp8-gemm-backend flashinfer_cutlass` | ⛔ SM120 路径，会让 L20 的 tuned FP8 config 失效 |
| `XTIER_THREADS=56`（SMT 兄弟核） | 比 32 差：每层 CPU 796 µs vs 625 µs |
| SPLIT_K（SM89 上） | ⛔ 负收益：N 维已够填满 GPU，多一次归约更慢 |
| 冷专家放 NVMe（`XTIER_COLD=1`） | 本机 1TB 内存没必要；且冷 read 不能减少 PCIe H2D 字节 |

## 十、踩过的坑

1. **续行命令中间的注释会吞参数**：bash 里 `cmd \` + 换行 + `# 注释` 会把该逻辑行剩余部分全当注释，
   而 `exec` 又会替换 shell → 后面的参数行根本没传给 SGLang。实际后果：`--disable-custom-all-reduce` 丢失
   → custom all-reduce 在无 P2P 的 GPU0+GPU2 上启动崩溃两次。脚本已改为参数数组 + `DRYRUN=1` 自检。
2. **运行中用 `cp` 覆盖 .so 会让调度器 SIGSEGV**：`cp` 先 `O_TRUNC` 再写，覆盖瞬间文件是残缺的，
   正好 dlopen 它的进程读到半个 .so。用 `tools/install-engine-libs.sh`（写临时文件 + `mv` 原子替换）。
3. **systemd(PID1) 丢过全部 fd**（2026-11-19 19:08）：`/proc/1/fd` 只剩 0/1/2，systemctl 全部超时。
   只能重启整机恢复（`daemon-reexec` 也走 D-Bus，同样卡死）。

## 十一、还没做的

1. SM89 小 M FP8 GEMM 的 split-K（源码级，见 5.2 的说明：本机实测是负收益，别做）
2. XTier prefill tile 自动调优器（仓库里没有现成工具，`sparse_mla` 的 tile 是为 99 KiB 硬编码的）
3. AMX（见第七节，需要分四步做，先做隔离 microbenchmark）
4. `XTIER_DECODE_MISS_GPU=0.05/0.1`（让 GPU 分担 decode 未命中专家；本机 CPU 很强，未必划算）
5. `XTIER_DRAFT_SLOTS=0/64`（每卡再省 3.36 GiB 给 KV 池）
