## 3. 最关键的一条：`--prefill-decode-interval 32`

**「多请求卡顿」的根因。** PDI=0 时，几个长上下文的 prefill 会连成一段几百秒的**连续 prefill**
（每个 32K chunk 约 8.5 秒；6 个 100K 请求共 20 个 chunk ≈ 170 秒），期间已就绪的请求
**一个 decode 步都跑不到**——一个请求可以 **116 秒发不出一个 token**。

| PDI | 8×4 聚合 | ITL p50 | **最大 token 停顿** | 8×4 TTFT p95 | 冷 prefill |
|---:|---:|---:|---:|---:|---:|
| 0 | 42.0 / 44.4 | 340 ms | **116,080 ms** | 7.1 s | 3488 tok/s |
| 16 | 45.2 / 52.9 | 47 ms | 339 ms | 6.0–10.3 s | 3526 tok/s |
| **32** | **56.5 / 55.7** | **45–67 ms** | **330 ms** | **7.9–8.9 s** | 3526 tok/s |
| 64 | 57.4 / 56.8 | 49 ms | 330 ms | 14.2–16.3 s | 3526 tok/s |

PDI=32 是平衡点。**验收要用延迟分布（`tools/bench_latency.py`），不能只看聚合吞吐**——
短提示基准（1.5K）永远触发不了这条路径。

## 4. 硬约束：两个 TP rank 不能放在同一个 NUMA 节点

XTier 的专家 worker 按 NUMA 节点放置（`xtier/engine/placement.py`），而 C 引擎选 worker CPU 的
`xtier_worker_cpus()`（`csrc/engine/engine.cpp`）**没有 rank 偏移**：两个 rank 在同一节点会拿到
**完全相同的 CPU 集合**。

实测（GPU0+1 + `XTIER_TP_NODES=0|0`）：两个 rank 的 29 个 worker 线程钉在同样的 29 个 CPU（100% 重叠），
每层 CPU 时间 257 µs → **8812 µs**（34×），单请求严重卡顿，加载期 Bus error / Segmentation fault。

→ **TP=2 必须一卡一节点 = GPU0+GPU2**（GPU1 是同节点的备用卡，不能和 GPU0 组 TP）。
→ 代价：两卡跨 socket，NCCL 走 UPI，无 P2P（所以要 `--disable-custom-all-reduce`）。

## 7. 踩过的坑（照抄会踩）

1. **bash 续行中间的注释会吞参数**：`cmd \` + 换行 + `# 注释` → 该逻辑行剩余部分全被当注释，
   而 `exec` 又会替换 shell → 后面的参数根本没传给 SGLang。实际后果：`--disable-custom-all-reduce` 丢失
   → custom all-reduce 在无 P2P 的 GPU0+GPU2 上启动崩溃两次。
   **脚本已改成参数数组**；改脚本后用 `DRYRUN=1 bash run-ds41-l20-tp2.sh` 打印真实参数清单核对。
2. **运行中用 `cp` 覆盖 .so 会让调度器 SIGSEGV**：`cp` 先 `O_TRUNC` 再写，覆盖瞬间文件是残缺的，
   正好 dlopen 它的进程读到半个 .so。用 `tools/install-engine-libs.sh`（原子替换），或先停服务。
3. **systemd(PID1) 丢过全部 fd**（2026-11-19 19:08）：`/proc/1/fd` 只剩 0/1/2，systemctl 全部超时。
   只能重启整机恢复（`daemon-reexec` 也走 D-Bus，同样卡死）。症状：`systemctl` 报
   `Failed to activate service 'org.freedesktop.systemd1'`。
4. **`XTIER_RECALL=1`（memory backend）会让并发下整个调度器卡死** → NCCL 集合通信超时 → watchdog SIGKILL。
   不要开。
5. **`XTIER_TILES_PROD=1` 的 128 宽 tile 是按大共享内存的卡设计的**（静态估算 120–144 KiB，
   SM89 只有 99 KiB）。实测能编译但只有 +2%，默认关着。
6. **别照抄网上那篇 4×RTX PRO 6000 的 chunk=2048**：它的前提是 all-reduce 走 PCIe switch（19.57 GB/s）；
   本机跨 socket 走 UPI，chunk 越小 all-reduce 次数越多反而更慢（2048 时只有 771 tok/s）。

## 8. 还没做的（接手后的候选）

0. **（排队中）unsloth 里的 Qwen**：`/opt/models/unsloth/Qwen3.8-Flash-Next-FP8`（173 GB / 132 个 safetensors），
   等 DeepSeek 这边调试结束再上。注意它与 GPU3 上 Strata 跑的那套**不是同一份权重**（Strata 用
   `/opt/models/orcarouter/...Uncensored-Q4_K_M.gguf`，GGUF + 自己的引擎）。XTier 有现成的 Qwen3.8 适配
   （`configs/qwen38-rtx4090-3090/`，目标 24 GB 卡，专家走 CPU 引擎），**GPU1 空着 48 GB 放得下**。
   起来之后**看板会自动多出一张卡**（`--dashboard --discover` 扫 `/proc` 找 `launch_server`），控制台不用再改。
1. **prefill tile 自动调优器**：仓库没有现成工具，`sparse_mla.py` 的 tile（`BLOCK_N=32,
   HEADS_PER_PROGRAM=32`）是为 99 KiB 共享内存硬编码的；prefill 的 GEMM 段还有空间。
2. **AMX**（Xeon 6530 支持）：XTier 目前 **AMX 指令数为 0**，用的是 `VDPBF16PS`。
   已量出 CPU 专家计算里算术占 58%（decode M=1–2）、带宽占 38%（M=8），
   但 AMX 的 tile 是 16 行而 decode 每个专家只有 1–2 个 token 行 → **收益可能被 tile 浪费 + FP4→AMX
   B-tile 在线重排吃掉**。要做按四步：① `dispatch.cpp` 加 AMX CPUID 检测 + `arch_prctl` 申请
   `XFEATURE_XTILEDATA` 权限、独立 `libxtier_engine_amx.so`；② 隔离 microbenchmark（必须把读 FP4 +
   反量化 + 重排都算进时间）；③ 有正收益再接 Gate/Up（`engine.cpp:710-749`）；④ 再接 Down
   （`engine.cpp:751-810`）。CPU prefill 比 decode 更可能获益（现在每 expert microgroup 上限 8 token，
   `XTIER_PREFILL_MICRO_TOKENS` 扩到 16/32 才有 AMX 的批量优势）。
3. `XTIER_DECODE_MISS_GPU=0.05/0.1`（decode 时 GPU 闲置，可让 GPU 分担未命中专家；本机 CPU 很强）。
4. `XTIER_DRAFT_SLOTS=0/64`（每卡再省 3.36 GiB 给 KV 池）。
5. **SM89 小 M FP8 GEMM 的 split-K**：本机实测是**负收益**（N 维已够填满 GPU），别做。
