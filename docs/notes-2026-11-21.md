## §14.43 并发硬顶 = 8 路（SM89 的结构性限制）

`--max-running-requests` 超过 8 时服务直接崩，原因是整条链路的退化：

```
bs > 8
  → CUDA graph 只能 replay bs 1..8
  → ragged_verify_layout = None
  → compact (ragged) verify 失效，退化成 static(rows_per_request = 5)
  → 跳过 JIT indexer planner（它要求 rows_per_request == 1）
  → deep_gemm.get_paged_mqa_logits_metadata 在 SM89 返回 None
  → assert 失败
```

过 8 只有三条路：**放弃 DSpark**（accept_len 3.5 → 1.0，不值）／**换 SM100+ 机器**／
**改 SGLang 上游 kernel 元数据规划器**（项目底线不允许）。⇒ 8 路就是这个部署的上限。

已排除的尝试：`MAXREQ=12`、`GRAPH_BS=12`、`--enable-deepseek-v4-fp4-indexer`
（`serving_hook` 直接拒绝：仅 SM100/SM120/gfx95）。

## §14.44 两个决定性的调参

| 改动 | 效果 |
|---|---|
| `XTIER_CACHE_ELASTIC_MAX_SLOTS` **43 → 64** | 专家缓存命中率 62% → 74%，4 路吞吐 **+33.1%** |
| `--schedule-policy` **lpm → fcfs** | 12 路 wall 216 s → 117 s，吞吐 **+80%** |

`MAX_SLOTS=64` 与 `XTIER_CACHE_SLOTS=43` + `BASE=0.5` 搭配（常驻 = floor(43×0.5) = 21，空闲时扩到 64）。
若把常驻提到 32（`SLOTS=64`），需要更多显存，会挤压 KV 池——不要与 `--mem-fraction-static 0.88` 一起改。

## §14.45 DSCP 投机解码的开关链（一个会让功能整个关闭的坑）

`DSPARK=1` 不只是打开一个开关，它还决定两个后续变量是否被 export：

```
DSPARK=1
  → export XTIER_DRAFT / SGLANG_RAGGED_VERIFY_MODE=compact
  → 附带 --speculative-dspark-block-size 5 --speculative-num-draft-tokens 6
```

脚本里 `DSPARK` 的默认值曾经是 **0**，而 unit 里写的是 1。
只在 unit 里写 1 本来没事，但一旦有人「直接跑脚本」（调试时最常见），
投机解码就**整个关掉**，accept_len 从 3.5 掉到 1.0——吞吐腰斩且没有任何报错。
⇒ 脚本默认值已改成 1，unit 同步，`verify_prod.sh` 现在会检查这条。

同理，`SPS_TABLE` / `MAMBA_CACHE` 原本**只有 unit 有**，脚本单跑时没有
`--speculative-dspark-sps-table-path` / `--max-mamba-cache-size` ⇒ 两处都已给脚本补上默认值。

## §14.46 输出漂移是引擎数值层的固有非确定性（不是 DSpark / 缓存 / RNG）

同一 prompt 重复请求偶尔给出不同答案，已逐项排除：

- 不是 DSpark 投机解码（关掉 DSpark 仍漂移）
- 不是弹性缓存换页（`XTIER_CACHE_ELASTIC=0` 仍漂移）
- 不是请求级 RNG（`seed` 在这条链路上不可靠，传了也不保证一致）

结论落在**引擎数值层**：CPU 专家的累加顺序会受工作窃取与 NUMA 分片影响，
在 logit 近平局处足以翻转 greedy 选择。这是「分块求和顺序不同」的经典后果，
与硬件无关、与 AMX 无关（AMX 只会让它更明显）。

实际影响可控：litellm 有 **60 秒 Redis 响应缓存**，重复请求在窗口内命中缓存，日常感知不到。

## §14.47 IOMMU A/B：`off` 零收益，保持 `on iommu=pt`

`iommu=pt` 本来就是本机原状，所以测的是更激进的一档：`intel_iommu=off iommu=off`。

| 指标 | `on + iommu=pt` | `off + iommu=off` | 变化 |
|---|---|---|---|
| 4 路服务端 avg_tps | 139.70 | 145.40 | +4.1% |
| 12 路服务端 avg_tps | 141.80 | 143.60 | **+1.3%** |
| 大上下文 prefill tok/s | 3738.23 | 3741.57 | **+0.1%** |
| prefill 期间 PCIe tx/rx | 0.57 / 0.14 MB/s | 0.57 / 0.14 MB/s | 0.0% |

**决策：回滚，保持 `intel_iommu=on iommu=pt pcie_aspm=off`。**

理由：
1. prefill 是 IOMMU 唯一可能影响的通道，实测 +0.1%，完全在噪声内。
2. 12 路 +1.3% < 事前约定的 +2% 门槛。
3. 4 路 +4.1% 落在**同状态跨重启噪声**内：同配置下独立基线 143.7 / 146.9 对本次 139.7 / 141.8，
   自身波动 2.8% / 3.5%，已经大于 on→off 的差值。
4. 机理：decode 期间 PCIe 只有 ~278 KB/s（GPU1 空闲时 36 KB/s，说明计数器是活的），
   prefill 期间 0.57 MB/s。专家权重走 XTier 自己的 CPU 引擎 + 主存，GPU 只留热槽。
   反过来把未命中专家搬去 GPU（`XTIER_DECODE_MISS_GPU=0.1`）实测 **−19.3%**，
   证明 PCIe 才是真瓶颈——IOMMU 的翻译开销根本不在关键路径上。

**测法上的坑（值得记）**：第一版基准是 decode 主导的，而 decode 几乎不产生 DMA，
光测 decode 一定会得出「没差别」的错误结论。**必须加 prefill 专项**才是 IOMMU 真正作用的通道。

## §14.48 `-mtune` 必须跟随构建主机

`csrc/CMakeLists.txt` 原来写死 `-mtune=znver4`（AMD Zen 4）。本机是 Intel，
同一份源码用 Zen 4 的调度策略编译，在 Xeon 6530 上明显更慢。

改成按 `/proc/cpuinfo` 的 vendor + flags 自动探测（Intel → `emeraldrapids`），
并把 flags 的 CMake 缓存改成 **FORCE**——否则在 AMD 主机上 configure 过的旧值会存活下来。

另一个坑：`-mtune` 只影响指令调度，**ISA 完全不变**（AVX512F/BW/CD/DQ/VL/BF16/VBMI 两家一样），
所以不会改变数值结果，只影响速度。长上下文 −12~13%。

3. **命令行参数不进 unit**（全在脚本的 `ARGS[]` 里）。

2. 新旧脚本 `DRYRUN=1` 的差异只有预期的 3 处
3. **新脚本 `DRYRUN=1` 输出 == 线上进程的 `/proc/PID/cmdline`** ⇒ 真的没改行为
4. **37 个 unit 变量 ↔ 脚本默认值 bad=0**

## §14.50 这一轮踩到的流程坑

1. **`sudo bash -c "..."` 里 `$` 会被外层 shell 展开** ⇒ 一律走 base64 送脚本。
2. **sudo 建的目录/文件属主是 root** ⇒ 用完要 `chown -R lenovo:lenovo`。
   本仓库曾被 root 写过：`.git/index`、`.git/HEAD`、`.git/ORIG_HEAD` 和 16 个对象都是 root
   ⇒ `git add` 报 `insufficient permission for adding an object`，用 `sudo chown -R lenovo:lenovo .git` 修好。
3. **md5sum 输出是 33 字节**（32 hex + `\n`），用 `wc -c` 判等会把正确的文件误判成不一致。
4. **`pgrep -f 'sglang.launch_server'` 可能匹配到执行命令的 shell 自身** ⇒ 用 `systemctl show -p MainPID`。
5. **`/proc/PID/environ` 只有 root 能读**，`/proc/PID/cmdline` 世界可读。
6. **`systemd-analyze verify` 要求文件名以 `.service` 结尾**，临时文件要带后缀。
7. **oneshot unit 被 `enable` 会在重启后自动用旧配置启动**，且 `systemctl start` 对已运行的 oneshot 是 no-op。
   诊断用的 unit 用完必须 `disable` + 删除。
8. **重启等待有竞态**：要先等「下线」再等「上线」。
9. **交叉校验的 sed 坑**：`s/^"//` 去不掉 `VAR="值"` 的值首引号（须 `s/="/=/`），
   且 `${VAR:-}` 空默认与 `${VAR:-/path}` 真默认会同时被 grep 命中 ⇒ 必须拆两张表。
10. **运行时 `cp` 覆盖 `.so` 会让调度器 SIGSEGV**（`cp` 先 `O_TRUNC`，瞬间是残缺文件）。
    用 `tools/install-engine-libs.sh`（原子 `mv`）或先停服务。
11. **bash 续行中间的注释会吞参数**：`cmd \` + 换行 + `# 注释` ⇒ 该逻辑行剩余部分全被当注释，
    后面的参数根本没传给 SGLang。实际后果是 `--disable-custom-all-reduce` 丢失，导致启动崩溃两次。
    **脚本已改成参数数组**；改完用 `DRYRUN=1 bash run-ds41-l20-tp2.sh` 核对。
12. **不要用 `tools/abkit.py` 的 `restore()`**——它恢复的是 `.bak-ab-baseline`（lpm 版），会冲掉 fcfs。
    回滚请用 `snapshots/prod/restore_prod.sh`。

## §14.51 AMX：可行，但属独立排期（本次不做）

本机 CPU 是 Emerald Rapids，`amx_bf16 / amx_tile / amx_int8` 全部为 YES，
但引擎只编译了 AVX512（`VDPBF16PS`），**AMX 指令数为 0**。
作者自带的 `tools/bench_cpu_ceiling.py` 实测算术占 60~68% ⇒ **专家计算是算力受限，不是带宽受限**。

改造点全部在 **XTier 自己的仓库**里，不在 SGLang 上游：

| 位置 | 内容 |
|---|---|
| `csrc/engine/engine.cpp` `gate_rows`（gate/up） | `_mm512_dpbf16_ps` |
| `csrc/engine/engine.cpp` `down_rows_bf16` | `_mm512_dpbf16_ps` |
| `csrc/engine/dispatch.cpp` `has_avx512()` / `load()` | 库选择，可加 `libxtier_engine_amx.so` |

**边界已核实**：SGLang（`/opt/sglang`，`sgl-project/sglang`）里搜 `xtier` 零命中；
XTier 是通过 `sglang.srt.plugins` 入口**反向 hook** SGLang 的，单向依赖。⇒ 改 AMX **不触碰上游源码**。

但有两个必须先定的前提：

1. **数值标准**：AMX 的 `_tile_dpbf16ps` 与 `VDPBF16PS` 语义相同（bf16 对、fp32 累加），
   但**累加顺序会变** ⇒ 不可能 bitwise 一致，只能做到「误差同量级 / PPL 不劣 / 采样分布等价」。
   §14.46 已证明这条链路上连现有内核都有漂移，所以「bitwise 一致」这个标准本身就不成立。
2. **工程量**：不是改两行。需要 tile 配置（`tilecfg` / `ldtile` / `sttile` 生命周期）、
   权重按 tile-major 重排（现有布局是 `unpack` 出来的 BF16 连续行）、
   SwiGLU/scale 的写入从 `reduce_add` 改成 `sttile` 后二次处理、
   再生成 `libxtier_engine_amx.so` 并让 `dispatch.cpp` 按 CPUID 选择。**属天级，非小时级。**

作者的建议路径（`docs/HANDOFF` 第 8 节）也要注意：decode 每个专家只有 1~2 个 token 行，
AMX 的 tile 是 16 行 ⇒ **decode 收益可能被 tile 浪费吃掉**；
真正有机会的是 **prefill**，但需要先把 `XTIER_PREFILL_MICRO_TOKENS` 从 8 扩到 16/32。

⇒ 结论：**技术上合法、收益不确定、工作量天级**。已记为待办，不在本轮实施。

**★ 这次踩的大坑（务必记住）**：

1. **rebase 中途 `git checkout <commit> -- <25 个路径>` 会覆盖工作区**。
   我为了救 3 个 root 属主的旧备份文件用了它，结果**把 `run-ds41-l20-tp2.sh` 等从磁盘上删掉了**
   （rebase 中途 HEAD 是重放中的版本，路径不存在 ⇒ `checkout` 把这些文件删了）。
   生产进程不受影响（bash 已读入内存），但盘上的脚本一度消失。
   **救法**：`git cat-file -p <old-commit>:<path> > <path>` 逐文件恢复，再核对 md5
   （脚本必须回到 `4540baf0ee1d8ae0b4b730df727fc501`）。
   **正确做法**：rebase 前先 `git stash`，或直接 `git worktree add` 开一个独立目录做重放，
   **绝不在生产目录里 rebase**。
2. **`.gitignore` 里写 `*.bak-*` 会把 `snapshots/prod/.align-bak/` 整个排除掉**
   （`*` 可以匹配 `.`）⇒ 需要补一条 `!snapshots/prod/.align-bak/`。
3. **`git stash pop` 在 rebase 中途会把改动恢复进重放中的中间状态**，看起来像
   「提交内容丢了」。要么 stash 在 rebase 前，要么 rebase 后再 pop。
4. **`git rebase --continue` 不会自动跳过已经做过的步骤**，
   出过一次错后 `done` 里会重复记录同一步，导致无限循环 ⇒ 出错就直接 `git rebase --quit`
   配合 `git update-ref refs/heads/main <new-head>`，不要在坏状态里挣扎。
5. **重建提交树的安全姿势**：`GIT_INDEX_FILE=/tmp/x.idx` + `git read-tree <tree>` +
   `git apply --cached <diff>` + `git commit-tree`，全程不碰工作区。
   最后用 `git reset --keep <new-head>` 移动分支——它会校验并保留工作区改动。
